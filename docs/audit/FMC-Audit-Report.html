Is it a demo or a secure application?It is both, and they must not be confused. (1) The server application (Node + Express + SQLite) has a real backend: server-side login, server-enforced permissions and department scoping, hashed passwords and sessions, an append-only event log. It is a sound foundation but not yet production-ready for real patient data (F-01, F-03 to F-11). (2) The single HTML file is a browser-only demo with its own tiny in-browser database; it is insecure by design and must only ever hold synthetic data (F-02).

B. Security and privacy findings

Classified by risk if the application held real patient data. Severity reflects impact and ease of exploitation.

Critical

F-01Critical

Published default password is auto-seeded on any empty database

Evidence
server/index.js:6 seeds all demo accounts unless FMC_SEED=0; server/seed.js:8 hard-codes "Demo-Passw0rd!"; the same password is in README. Probe P9a: all 10 accounts share it, including admin.
Impact
Anyone who has read the README can sign in as Administrator on a fresh install and see every patient.
Recommended fix
Remove the default password. First start shows a one-time setup screen that creates the Super Administrator with a generated one-time password and forces a change. Refuse to start in production if a default-password hash exists. Seed data only behind an explicit FMC_DEMO=1.
F-02Critical

The single-file HTML demo is not a secure application

Evidence
src/demo/*: database, login and "server" run in the browser. Records are saved unencrypted in localStorage (key fmc_demo_db); passwords use a demo SHA-256 stand-in (src/demo/crypto-shim.js). Anyone holding the file can read or change everything.
Impact
If real patient data were typed into the demo it would sit unprotected in the browser, outside UAE control, with no audit trail.
Recommended fix
Keep the demo for training with synthetic data only, add a persistent red "DEMO – no real patient data" banner, and never distribute it as the production system. Production = the server application only.

High

F-03High

Patient directory visible to every signed-in role

Evidence
server/app.js:208 → registration.js:145: GET /api/patients has no department scope and no minimum query length. Probes P1/P1b/P1c: a Physiotherapy clinician found an Orthopedics-only patient (name, DOB, phone), the query "%" returned the whole directory, and phone numbers can be looked up.
Impact
Violates least privilege and patient privacy; a curious or compromised clinical account can harvest demographics.
Recommended fix
Restrict search by role and department (reception/administration: all; clinicians: patients with a visit, appointment or queue entry in their departments). Require 3+ characters, escape % and _, rate-limit searches, and log the patients returned. Add audited break-glass access with a mandatory reason.
F-04High

No way to change your own password or username; no first-login change

Evidence
Probe P10: POST /api/account/password → 404; the UI has no account page. Usernames cannot be edited (P10b). Admin-set passwords are known to the admin and never expire.
Impact
Credentials can never be rotated by their owners; shared or admin-known passwords defeat individual accountability.
Recommended fix
My Account page: change password (current password required), session list with "sign out other sessions", username rules. Admin-created accounts get a one-time invitation link or temporary password with forced change at first login.
F-05High

No multifactor authentication

Evidence
Probe P10e: no MFA endpoint. Administrators and clinicians sign in with a password only. (Vendor summaries of ADHICS say MFA is expected for administrative access; the primary DoH text could not be fetched from this environment, so this must be verified.)
Impact
A single phished or guessed password gives full access to patient data and settings.
Recommended fix
TOTP (RFC 6238) with recovery codes using an established library; mandatory for Super Administrator and Clinic Manager, optional or required by policy for others; step-up re-authentication for sensitive actions.
F-06High

Brute-force protection is weak and enables lock-out attacks

Evidence
server/app.js:47,74: in-memory counter per IP+username, 5 attempts per minute, resets on restart, no alerting. Probe P5: 7 wrong guesses made the real administrator unable to sign in (429).
Impact
An attacker can keep the administrator locked out; a slow attacker is not stopped; behind a reverse proxy every user shares one IP.
Recommended fix
Persistent per-account progressive delay plus per-IP limits, no hard lock-out of administrators by anonymous traffic, alerts to Super Administrators, configured trust-proxy, and an admin unlock action. All recorded in the audit log.
F-07High

The last administrator can be disabled or demoted

Evidence
Probe P7: an admin deactivated their own (only) admin account → 200; the next request returned 401.
Impact
Nobody can reach Settings again without editing the database file.
Recommended fix
Block disabling/demoting the last active Super Administrator; require at least two; add a documented, audited recovery procedure.
F-08High

Access model does not match how FMC works

Evidence
server/db.js:36 allows four fixed roles; users.department_id (db.js:37) allows one department. Probe P31. Permissions are hard-coded in server/perms.js.
Impact
Shared staff, staff covering two departments, a Clinic Manager, GP, Orthopedic Doctor or generic authorized clinician cannot be modelled without code changes.
Recommended fix
Role templates stored in the database (editable permissions), per-user department grants (many-to-many) plus the existing per-service authorization, and separation of duties (Super Administrator manages access, not treatment).
F-09High

Audit trail cannot show who looked at which patient, and is not tamper-evident

Evidence
Probe P1d: patient searches store only the query length. Queue, dashboard and sessions views (which show patient names) are not logged. Probe P17: dropping the audit_no_delete trigger lets anyone with database write access delete audit rows. Password reset and role change are not distinct audit events.
Impact
Cannot answer "who accessed this patient" for investigations; audit evidence could be altered without detection.
Recommended fix
Log every patient-record read with user, patient, endpoint, reason and time; distinct events for password reset, role/department/service changes, session revocation and lock-outs; hash-chain the log and ship it off-host (append-only storage); alert on gaps.
F-10High

Live database is stored unencrypted with permissive file permissions

Evidence
/tmp/fmc-e2e.db created with mode 644 (world-readable); WAL file alongside; idempotency_keys keeps a copy of the patient JSON for 2 days. Backups are encrypted (tested), the live file is not.
Impact
Anyone with server file access reads all patient data.
Recommended fix
Restrict data/ to 0700 and files to 0600, move idempotency payloads to ids only, use disk/volume or database encryption at rest, and keep keys in a secret manager.
F-11High

No production deployment, TLS or UAE data residency decision

Evidence
App serves plain HTTP; cookie is Secure so login fails over http on a non-localhost address; no HSTS. Federal Law No. 2 of 2019 (Art. 13) restricts storing or moving health data outside the UAE (per law-firm summaries; verify with counsel).
Impact
The system cannot safely hold real patient data until hosting is chosen and secured.
Recommended fix
Decide hosting (see Section E). Terminate TLS 1.2+ at a reverse proxy, enable HSTS, run the Node service as a non-root user, and document the environment.

Medium

F-12Medium

Usernames exposed to every user

Evidence
Probe P3: GET /api/staff (server/app.js:109) returns all usernames to a clinician.
Impact
Hands attackers half of each credential.
Recommended fix
Return usernames only to Super Administrators; show names elsewhere.
F-13Medium

Login timing reveals which usernames exist

Evidence
Probe P4: unknown user 3.7 ms vs real user 51 ms per attempt (hash only computed for real accounts).
Impact
Account enumeration.
Recommended fix
Always run a dummy hash for unknown users; return identical responses.
F-14Medium

Password hashing blocks the whole server

Evidence
Probe P6: 12 concurrent logins delayed an unrelated request by ~240 ms (scryptSync, server/app.js:11,16).
Impact
A login flood becomes a denial of service for ward staff.
Recommended fix
Use asynchronous hashing off the main thread. Prefer Argon2id (OWASP first choice); scrypt with N=2^17 is an accepted alternative. Re-hash on next login. (Decision E-4.)
F-15Medium

Weak password rules

Evidence
Probe P10c: "aaaaaaaaaa" accepted; only a 10-character minimum.
Impact
Easily guessed passwords on clinical accounts.
Recommended fix
Length-first policy (12+), block common/breached passwords, no composition tricks, allow passphrases; never show or email passwords.
F-16Medium

Sessions have no absolute lifetime, list or revoke

Evidence
server/app.js:53-54 enforces idle time only; cookie Max-Age is fixed at login (:84). Probe P10d: no session list/revoke.
Impact
A stolen token on an active device stays valid indefinitely.
Recommended fix
Idle timeout 15–30 min for clinical workstations (configurable), absolute lifetime 12 h, session list with device/IP, "sign out everywhere", automatic revocation after password, role or permission change.
F-17Medium

Security headers incomplete

Evidence
Probe P25: present CSP, X-Content-Type-Options, X-Frame-Options, Referrer-Policy; missing Strict-Transport-Security, Permissions-Policy, Cross-Origin-Opener-Policy.
Impact
Weaker browser-side protection once on HTTPS.
Recommended fix
Add the missing headers; remove style-src unsafe-inline when styles are externalised.
F-18Medium

Invalid input can return HTTP 500; DB error text can reach the user

Evidence
Probe P8: role="wizard" → 500. Config CRUD returns constraint text (server/app.js:126 handlers).
Impact
Poor validation experience; minor information disclosure.
Recommended fix
Central schema validation (e.g. zod) with 400 responses and generic messages.
F-19Medium

Departments can be deactivated while patients are queued

Evidence
Probe P18: PATCH {active:0} with an open queue entry → 200.
Impact
Patients stranded in an inactive department.
Recommended fix
Block or require a reassignment step; warn about open visits, rooms and staff.
F-20Medium

Shared hall shows "Occupied" with free beds

Evidence
Probe P27: PT-HALL-01 shows OCCUPIED at 1/6 beds (server/ops.js:91); dashboard "Rooms free" excludes it.
Impact
Reception under-uses capacity; KPI is misleading.
Recommended fix
Show "Partly used 1/6" and count free beds.
F-21Medium

Missing everyday reception tools

Evidence
Probes P29/P30: no cancel/no-show for a queue entry, no patient edit or merge; no appointment creation screen (API exists, no UI).
Impact
Walk-aways stay "waiting"; typos in demographics cannot be fixed.
Recommended fix
Cancel/no-show with reason, audited demographic edit with approval for MRN/DOB, merge workflow, appointment screen.
F-22Medium

Backups are manual and policy values are unset

Evidence
server/backup.js works and restores (tested) but nothing schedules it; retention intentionally unset.
Impact
No recovery point if the server fails.
Recommended fix
Scheduled encrypted backups to a second UAE location, restore drills, alerting (Health page already shows staleness).

UAE and Abu Dhabi requirements: what could and could not be verified

No compliance claim is made. Official documents on doh.gov.ae could not be opened from this environment, so control-level wording below comes from search summaries and must be confirmed against the primary texts by FMC's compliance officer.

  • ADHICS (Abu Dhabi Healthcare Information and Cyber Security Standard): issued by the Department of Health, applies to health entities in Abu Dhabi, tied to licensing; reported to have ~692 controls in 11 domains, tiered by entity type; a Version 2 is reported (2024) — confirm the current version. Secondary sources mention MFA for administrative access, role-based access with revalidation, encryption of patient data exchanged electronically, asset classification, and periodic vulnerability testing. Sources: DoH ADHICS (2019 text), DoH ADHICS FAQ, DoH announcement.
  • Federal Law No. 2 of 2019 (ICT in health fields): law-firm summaries report that health data may not be stored or transferred outside the UAE without approval (Art. 13), and must be kept at least 25 years from the last procedure (Art. 20). Implementing regulations and exemptions need checking. Sources: Al Tamimi, Latham & Watkins, PwC.
  • Malaffi (Abu Dhabi health information exchange): participation is reported as mandatory for DoH-licensed facilities, with coding standards and recent data-reporting circulars. An EMR must be able to integrate. Sources: Al Tamimi, DoH HIE resources.
  • Implications for this plan: UAE-resident hosting; 25-year retention design (never hard-delete clinical records); MFA for administrators; full access logging; encryption; independent security testing; integration path to Malaffi. FMC should obtain ADHICS and the HIE policy from DoH and run a formal gap assessment.

D. Implementation plan

Order is by risk. Each phase ends with tests; existing data and working features are kept. Effort figures are estimates for planning only.

Phase 0 — Immediate critical fixes

No architecture change. About 1–2 days.

Remove default credentials and add first-run setup · scope and harden patient search · hide usernames from non-admins · protect the last Super Administrator · validate roles (400 not 500) · dummy-hash for unknown users and asynchronous hashing · absolute session lifetime · 0700/0600 file permissions · missing headers · persistent DEMO banner · accessible label.

Tests: F-01, F-03, F-07, F-12, F-13 probes flip to "ok".

Phase 1 — Accounts and user management

About 1 week.

My Account (change password with current-password check, sessions list and sign-out-others, username rules) · admin: create account, invitation link or temporary password with forced change, reset, disable/reactivate, revoke sessions, account activity · password policy · rate limiting redesign.

Tests: login ok/bad, password change, reset, disabled account, expiry, lock-out behaviour.

Phase 2 — Roles and departments

About 1 week.

Role templates in the database (Super Administrator, Clinic Manager, Receptionist, Physiotherapist, Orthopedic Doctor, General Practitioner, Authorized Clinical Staff) · many-to-many department access · keep per-service authorization · separation of duties · UI to manage them · migration that keeps existing users and records.

Tests: department isolation, escalation attempts, multi-department staff.

Phase 3 — Multifactor authentication

About 3–4 days.

TOTP + recovery codes, enforced for Super Administrator and Clinic Manager, step-up for sensitive actions.

Tests: enrolment, wrong code, recovery, enforcement.

Phase 4 — Privacy and audit

About 1 week.

Patient-access log, break-glass with reason, distinct security events, hash-chained audit with off-host export, viewer with filters, retention setting.

Tests: audit integrity, access-log completeness, tamper detection.

Phase 5 — Workflow corrections

About 1 week.

Hall occupancy and KPI, cancel/no-show, patient edit/merge with approval, appointment screen, check-out warnings, department deactivation safeguards.

Tests: concurrent room assignment, check-in/out, treatment timing and reports.

Phase 6 — UI/UX and branding

Runs alongside phases 1–5.

Account, Users, Sessions, Security and Audit screens; mobile and Arabic review; accessibility pass; use the original FMC logo with "Al Faisal Medical Center · Ideal Care · الرعاية المثالية".

Browser tests in English and Arabic, phone and desktop.

Phase 7 — Deployment and assurance

Depends on decisions below.

UAE-resident hosting, TLS, reverse proxy, secret management, scheduled backups and restore drills, monitoring, independent penetration test, ADHICS gap assessment with FMC compliance officer.
